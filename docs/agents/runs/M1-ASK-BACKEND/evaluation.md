# Routing evaluation

Command actually run (root virtual environment):

`PYTHONPATH=. ./.venv/bin/python tests/test_ask_routing_evaluation.py`

The checked-in fixture contains 250 repositories: 25 feature services and 225 realistic tooling/catalog distractors. Fifty user tasks describe customer outcomes and feature terminology using plurals, tense changes and paraphrases. Five extra tasks require two repositories. All IDs/metadata/source are synthetic. Actual GitHubService discovery (injected HTTP transport), actual IndexService catalog/search/source and real SQLite/jobs are used. Twenty-five repositories have indexed snapshots. No embeddings or model calls run; semantic degradation is disclosed by routing. A test-only temporary synthetic credential vault and generated test signing key are inherited from the existing GitHub test fixture; no configured credentials are read.

Final answerable top-three recall: **50/50 (100%)**. Basic unexpanded `IndexService.catalog_candidates(prompt, limit=3)` lexical baseline: **49/50 (98%)**. Multi-repository top-three label recall **10/10 (100%)**; all expected repositories covered **5/5 (100%)**, same as baseline. Two ambiguous requests require selection; two absent requests return no_match. Short-name collision requires selection, owner-qualified selection is correct, revoked candidates disappear, missing pins require selection. Raw final measurements are in routing-results.json.

Routing uses deterministic word-form expansion and removes generic action/function-word matches, then bounded actual source retrieval on strongest candidates. It does not infer calibrated confidence or ask a model to invent repository names. Generic feature matches remain selection requests even when recall is high. This benchmark is a development set used while tuning those two simple rules, **not a held-out accuracy estimate**. The catalog has broad but synthetic domain separation and many tooling distractors; a real user's catalog will be harder. No latency SLA or live model quality claim is made.

An initial local/demo-only attempt (same feature fixture, README bodies instead of GitHub descriptions) measured **12/50 (24%)** single-task top3 recall, **6/10 (60%)** multi-label recall and **1/5 (20%)** complete multi-repository coverage. Candidate d8f1005 exposes filenames in generated profiles, not README body terms. Bounded source retrieval only after candidate generation cannot recover repositories absent from that candidate list. The authoritative GitHub metadata evaluation above tests a separate supported route; it does not erase this limitation. Index owner/coordinator should improve source-backed catalog profiles in its exclusive scope and rerun both modes. This task does not modify that dependency.
